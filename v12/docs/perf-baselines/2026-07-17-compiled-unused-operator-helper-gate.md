# Compiled unused-operator-helper gate (2026-07-17)

## Outcome

The package-boundary audit is complete and retains no compiler, runtime, VM,
stdlib, workload, or verifier change. Current static executables already avoid
interpreter construction, program evaluation, default-body AST decoding, and
concrete interpreter storage in the compiler bridge. For the five audited
applications, the only remaining concrete interpreter roots in generated root
code are the unconditional calls to `interpreter.ApplyBinaryOperatorFast` and
`interpreter.ApplyUnaryOperatorFast` inside generic operator helper definitions.

Four applications never call either helper: Binary Trees, Base64, Dependency
Plan, and Option/Result Configuration. Document Audit makes one reachable
binary-helper call. It comes from `String.substring` after `length != nil`:
the compiler boxes the guarded `?i32` and zero, dispatches `<` through
`__able_binary_op`, and unboxes the boolean result.

An initially confusing guard build was generated by the stale checked-in
`v12/interpreters/go/able` executable. Rebuilding the CLI from the current
source produced the expected no-bootstrap form. Generated-code audits must use
a freshly built CLI or `bench_perf`, not a possibly stale workspace binary.

## Candidate

A temporary general dead-helper candidate:

- emitted binary/unary operator helpers only when generated code called them;
- imported the concrete interpreter only when the final generated file still
  contained an interpreter reference; and
- retained the existing helper implementation unchanged whenever reachable.

This was based solely on generated reachability, not an application or named
type. Focused compiler tests proved both omission and retention. Generated
Dependency Plan, Option/Result Configuration, Binary Trees, and Base64 binaries
fell from 329 interpreter symbols to zero. Document Audit correctly retained
424 interpreter symbols.

## Verifier-backed timing gate

Baseline and candidate binaries were run as alternating independent processes
under the scorecard execution contracts. Every recorded process passed its
external verifier. The workstation is shared, so the volatile Binary Trees
guard received three five-pair cohorts.

| Application | Baseline mean | Candidate mean | Decision signal |
| --- | ---: | ---: | --- |
| Document Audit (5 each) | 0.070 s | 0.076 s | unchanged dependency; noise |
| Dependency Plan (5 each) | 0.070 s | <0.01 s | large startup win |
| Option/Result Config (5 each) | 0.226 s | 0.128 s | 43.4% faster |
| Base64 (7 each) | 2.181 s | 2.033 s | 6.8% faster |
| Binary Trees (15 each) | 7.324 s | 7.587 s | 3.6% slower |

Binary Trees cohort means were respectively 7.964/8.448 seconds,
6.930/7.048 seconds, and 7.078/7.266 seconds for baseline/candidate. The
direction repeated after order reversal and additional averaging. Because
Binary Trees is a stable target-meeting compiled row, the 3.6% combined
regression fails the broad benchmark bar despite the startup and size wins.
The candidate was fully reverted.

## Next gate

Do not retry unused-helper omission, linker ballast, lazy fixed-integer cache
initialization, generated registration micro-tuning, or named-container
lowering. The next useful feasibility tranche is a shared boxed primitive
operator package boundary. The current fast operator implementation mixes two
concerns: general boxed primitive semantics and bytecode-private raw integer
carriers. Separating those concerns could let generated executables retain a
small, semantically complete operator layer without importing the full
interpreter, while the VM keeps its raw-carrier path.

That work should begin as an extraction audit, not a rewrite: inventory every
numeric promotion, overflow, division, comparison, string, unary, and dotted
bitwise dependency; define parity tests against the current interpreter fast
path; and advance only if the boxed layer remains primitive-only and the same
package cut serves Document Audit, Dependency Plan, and Option/Result
Configuration. Any candidate must repeat the three application measurements
and the Binary Trees/Base64 guards. This is preferable to special-casing the
one nullable comparison because it preserves the project-wide semantic path
and addresses the exact shared package dependency.
