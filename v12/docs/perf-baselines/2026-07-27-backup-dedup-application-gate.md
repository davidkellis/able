# Backup Dedup application gate

Date: 2026-07-27

## Decision

Retain the portable `backup_dedup` application, its source-equivalent
Go/Python/Ruby implementations, exact verifier, catalog and coverage
memberships, five-run selected measurements, and bounded profiles. Retain no
compiler, generated-runtime, runtime, interpreter, bytecode VM,
canonical-stdlib, language, dependency, or WASM production change.

The new application is a valid frontier invalidation because it adds a real
content-defined backup-deduplication shape to the previously reviewed
61-application corpus. Its strict compiled profile does expose a material
native-to-`runtime.Value` transition, but that transition is the already
closed runtime-backed generic nominal storage boundary. Its bytecode profile
repeats already closed arithmetic, typed-integer, stack, Array, and map
families. No new exact removable owner passes the three-unlike-application
admission rule.

The compact machine-readable companion is
`2026-07-27-backup-dedup-application-gate.json`.

## Application contract

The workload reads the existing 128 KiB Markdown corpus as raw bytes, applies
a rolling content-defined chunk boundary, hashes each chunk, and records
deduplication counts in `HashMap i64 i64`. It exercises native byte-Array
reads, bounded integer arithmetic, nominal `Chunk` and `DedupTally` values,
inherent methods, `Option` matching, file arguments, loops, and branches.

## Compiled ownership

The strict binary was generated with `--no-fallbacks`. Its final Go module
contains 96 dependencies and no `able/interpreter-go/pkg/interpreter`
dependency.

Three independent main-only CPU profiles merge to 280 ms of samples:

| Exact flat owner | Share |
| --- | ---: |
| `__able_divmod_signed` | 46.43% |
| `__able_checked_mul_signed` | 21.43% |
| `__able_checked_add_signed` | 14.29% |

Those are the established checked-arithmetic families. The generated byte
Array remains `[]uint8`, application integers remain native Go integers, and
the hot application body does not enter the interpreter.

Two exact main allocation processes each recorded 2,011,064 bytes and 47,027
allocations. Excluding profile serialization, the representative exact
attribution contains 1,467 KiB and 31,296 objects in
`bridge.ToDynamicI64`, plus 118.44 KiB and 7,580 objects in
`__able_nullable_i64_from_value`. Generated source shows why:
`HashMap_i64_i64.raw_get/raw_set` accept native `int64`, encode handle, key,
and value as `runtime.Value`, call the shared runtime-backed map semantics,
then recover the nullable native result.

This is the same generic storage boundary previously measured in
K-Nucleotide, Inventory Reconciliation, and Word Frequency. A rule naming
`HashMap` would violate the project guardrail. Removing the boundary
generally requires a typed storage and identity design for all generic
nominals, including user-defined nominals, aliasing, mutation, iteration,
interfaces, imports, and dynamic fallback materialization. The new evidence
does not make that architectural rule safe as a local compiler fast path, so
`compiled-text-map` remains `closed-no-shared-leaf`.

## Bytecode ownership

Three clean warmed main-only profiles merge to 18.92 seconds of CPU samples
and average 6.351 seconds, 75,057,624 bytes, and 8,616,697 allocations per
32-round operation.

`runResumable` owns 13.69% flat and 99.21% cumulative. Exact flat descendants
include `execBinary` at 3.70%, `bytecodeRawIntegerValueInfo` at 3.49%,
`evaluateDivModFast` at 3.44%, raw `i64` stack reads at 2.17%, checked stack
append at 2.06%, and integer fit checks at 2.06%. These are the same exact
typed-integer, arithmetic, frame/stack, and dispatcher families covered by
the current corpus-wide owner census and prior rejected broad candidates.

A separate trace records 8,513,837 calls. It proves 4,194,304 byte reads use
`array_read_slot_mono_u8_fast`, 4,194,336 length calls use
`array_len_fast`, and all 15,648 `raw_get` and 15,648 `raw_set` method calls
use the existing inline/native dispatch paths. There is no missed Array or
method-call lowering hidden beneath the profile. `bytecode-text-map` remains
`closed-rejected-candidate`.

## Next recommendation

Keep production mutation paused and perform one report-only admission review
of a general typed generic-nominal storage design only if a future semantic
or application invalidation makes it concrete across unlike user-defined as
well as stdlib nominals.

Why: Backup Dedup independently confirms that primitive and Array lowering is
already native and interpreter-free; its material remaining compiled boundary
is generic nominal storage, not an accidental compiled/interpreted crossing.
The same boundary is important, but optimizing only `HashMap` would create the
forbidden named-container rule.

What it entails: define representation, identity, mutation, aliasing,
iteration, interface, import, and fallback-materialization invariants for
typed storage shared by every generic nominal. Before implementation, prove
one exact compiler/runtime rule reaches at least three unlike applications
and includes a user-defined nominal control. Then require semantic guards and
five-or-more balanced verifier-backed Able baseline/candidate/Go cohorts.

Why it is important: this is the architectural path that could remove the
remaining boxing visible here while preserving the language contract. The
evidence bar prevents a benchmark-specific shortcut from masquerading as
native Go lowering. Do not begin WASM work.
